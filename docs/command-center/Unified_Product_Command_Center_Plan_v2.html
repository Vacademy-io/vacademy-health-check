Unified Product Command Center

Feature plan, v2 · Vacademy super admin portal · 3 November 2026

The plan: add a Command Center module to the Vacademy super admin portal. It brings website traffic and funnel events from the four product sites together with logins, usage, AI token use and platform billing from the shared backend, into one analytics store. From the same screens you can create demos, start trials, and suspend, terminate or recreate accounts. v2 builds on what the portal and backend already have instead of rebuilding it.

0. What changed from v1

  • Product names corrected: Vacademy.io, Voomsales, Telleo and Evalezy.
  • Reuse, don't rebuild: Razorpay billing, demo provisioning, login/activity data, token metering and change history already exist (§1.3).
  • No second Razorpay webhook. Revenue reads admin-core's platform billing, so there is one source of truth for payments.
  • Where things run: the portal has no server, so ingestion runs in community-service (§2.1).
  • External connections listed one by one, with what exists and what is missing, checked against the code on 3 Nov 2026 (§2.2).
  • Sign-in entry points: Vacademy.io, Telleo and Evalezy share dash.vacademy.io; Voomsales signs in at app.voomsales.com (§2.3).
  • New prerequisite: a product entitlements table. Today an institute can carry only one product (§2.2, §6).
  • GA4: user_id is now the real user ID, with institute_id as a user property (§3).
  • Consent and retention section added for the visitor cookie (§3.4).
  • Funnel corrected: login clicks come from existing customers, so they're out of the funnel. Demo and trial are two branches (§4).
  • State machine fixed: a new Expired state, plus missing edges such as Suspended → Active and Demo → Active (§5).
  • Actions split: per-product actions vs account-level actions (§5).
  • Destructive actions are limited to named usernames (§1.2).
  • Metric definitions tightened: visitors, churn, trial-to-paid and MRR (§7).
  • Rollout reordered: Revenue moves to Phase 1 because its data already exists (§8).

1.1 Decisions already made

  • One institute ID is shared across all four products. The account list and Account 360 key on it. Voomsales will move to Vacademy auth-service and the same institute IDs (§2.3).
  • Token usage is already tracked. The Command Center reads it and doesn't rebuild it.
  • Razorpay is the payment gateway, through the platform billing that already exists in admin-core.

1.2 Who can use it

The PM is the main user in v1, and there is no full role model. But the portal already admits every username on the PORTAL_ALLOWED_USERS allowlist, which is enforced by the portal's Cloudflare proxy. So Suspend, Terminate and Recreate are also limited to a short list of named usernames. Every destructive action needs typed confirmation and writes an audit entry.

2. Architecture

The Command Center never queries GA4 or Razorpay live when a page opens. Website data is synced into one analytics store on a schedule, and backend data is read where it already lives. Dashboards load fast and every product is measured by the same definitions.

2.1 Where ingestion runs

The portal is a static app behind a Cloudflare Pages proxy and has no server of its own. The GA4 sync job, the /track endpoint and the nightly aggregates run in community-service:

  • It already hosts the public onboarding, pricing and status endpoints, allow-listed in CommunityApplicationSecurityConfig.
  • It can use the @Scheduled + ShedLock pattern already used in admin-core.

Store: a separate analytics schema in the existing Postgres. Raw events move to ClickHouse or BigQuery only if volume makes dashboards slow.

Access to collect in Phase 0:

  • A Google service account, with Viewer access on each GA4 property (including the one inside the GTM container).
  • Named owners for the Telleo and Evalezy site repos.
  • No new Razorpay keys: the platform credentials are already stored in admin-core.

2.3 Sign-in entry points

  • Vacademy.io, Telleo and Evalezy sign in at dash.vacademy.io: one login and one institute ID for three products.
    • The login can't say which product it's for. Product is decided in two ways:
      • Arrival: each site's Login link carries ?product=…&visitor_id=…, and the dashboard stores it on the session.
      • Feature use: calls = Telleo, evaluations = Evalezy, LMS activity = Vacademy.io. Per-product activity and activation use this.
    • Only one app needs instrumenting for these three products. It already sends a Login Success event to Amplitude; add a product property.
    • A suspended product can't block login, because the login is shared. Instead, its features are switched off through institute modules.
  • Voomsales signs in at app.voomsales.com/login.
    • In its current code the login is front-end only (it doesn't check credentials), and the CRM screens use a mock institute.
    • Decided: Voomsales will authenticate through Vacademy auth-service with the same institute IDs.
    • Until then, Voomsales contributes website traffic and demo leads only. Accounts, logins, usage and lifecycle actions start working once it's wired.

3. Event tracking plan

All four sites and products send the same event names with the same parameters, which is what makes a combined funnel possible.

EventFires whenWhere

cta_login_clickLogin button clickedAll marketing sites (returning-customer metric, not the funnel)
cta_book_demo_clickBook a demo clickedAll marketing sites
demo_form_submitDemo lead accepted by the backend lead-submit endpointServer side
cta_trial_clickStart free trial clickedAll marketing sites
trial_signup_completeTrial account createdServer side
login_successUser logs inServer side, from existing session data

pricing_view / checkout_startPricing page seen / payment link openedSites and in-app billing

vacademy.io already sends demo_request to GTM, and Voomsales sends generate_lead. Rename both to the standard names, or map them in GA4.

3.1 Parameters on every event

product (vacademy, voomsales, telleo, evalezy), visitor_id, institute_id (once known), page_path, utm_source / utm_medium / utm_campaign, device, country / state.

3.2 Linking a website visitor to an institute

The sites are on separate domains (vacademy.io, voomsales.com and the Telleo and Evalezy sites), so they can't share a cookie. Instead:

  • First visit: after consent, the tracker sets a first-party visitor_id cookie and keeps the first-touch UTM values.
  • CTA click: Login, Book a demo and Start trial links carry visitor_id, product and the UTMs as URL parameters, to dash.vacademy.io or app.voomsales.com.
  • Lead submit or signup: the backend saves visitor_id against the new institute ID. From then on, every earlier visit is attributed to that institute.

3.3 GA4 identity

Set GA4 user_id to the real user ID, and send institute_id as a user property. (v1 used the institute ID as the user ID, which would merge every user in an institute into one GA4 "user".) Don't send personal data such as emails or phone numbers to GA4.

3.4 Consent and retention

  • Consent banner: a site-wide banner on all four sites, with GA Consent Mode. visitor_id is set only after consent.
  • Retention: raw web events are kept for 13 months; daily aggregates are kept indefinitely.
  • Visitors who never sign up: their visitor records are deleted after 13 months.
  • Legal review: wording and data handling are reviewed against India's DPDP Act 2023 before launch.

5. Account lifecycle

Each institute has a state per product, because an institute can be paid on Vacademy.io while trialling Telleo.

5.1 Mapping existing data

  • Lead tags: LEAD → Lead, FREE_TRIAL → Trial, PROD → Active. TEST accounts are excluded from every metric. After migration the tag is derived from the state, so there is one source of truth.
  • Existing demos in institute_trial become Demo state for vacademy.

Thresholds such as "3 days in 7" are starting points; tune them after a month of data.

8. Rollout

Visibility ships first. Revenue moves up to Phase 1 because its data already exists.

Dependencies

  • Backend (Phase 0): the product_entitlements table, and an institute status checked at login for account suspend.
  • GA4 access: property IDs and Viewer access for the service account, including the GA4 property inside the vacademy.io GTM container.
  • Site work on all four sites: tracker snippet, standard CTA event names, CTA links that carry visitor_id/product/UTMs, and a consent banner.
  • Owners: named owners for the Telleo and Evalezy sites.
  • vacademy.io demo form: "Book a demo" posts to the backend lead endpoint instead of only opening Google Calendar.
  • Voomsales: the login uses Vacademy auth-service and real institute IDs instead of the mock institute.
  • Revenue coverage: core LMS subscriptions are billed through platform billing. Until they are, Revenue covers AI plans and credit packs only.
  • Demo templates: one template institute per product, with realistic sample data (Phase 2).

Open questions

  • Trial length and usage caps per product (for example, 14 days and a token cap on Telleo)?
  • How long is an Expired trial kept before it can be terminated, and how long is terminated data held before purge? (30 days is the default.)
  • Should prospects be able to self-serve a demo from the website, or is demo creation PM-only?
  • Which plans and prices go into platform billing first, and are any annual?
  • Which usernames may run Suspend account, Terminate and Recreate?
  • Are Telleo and Evalezy API customers always institutes with a Vacademy institute ID, or can an API key belong to someone else?
  • Ingestion host: community-service (proposed) or Cloudflare cron triggers?
